# 小红书团餐实拍图文

团餐文案默认写给实际订餐的人。商家号可以直接说在做什么、这餐怎么配、怎样问价，语气像在接待一位来问饭的人。

## 工作方式

1. 先确认本次交付。只有文案改稿时读现有图序和文案，按原页序写。只有排版任务时优先用现有正文理解主题。制作完整图集时，从用户给的照片或已通过质检的抽帧中挑选可用图，建立原图与成品的对应。
2. 看照片能说到哪一步。餐盒摞在备餐台上可以写装盒。车、送达地点、取餐对象或交接过程各要有相应素材或用户事实支持。拿不准是不是同一个项目、同一天或同一批餐时，用几张照片并列记录。
3. 根据主题挑封面和翻图顺序。先用一张具体照片建立看点，第二张接住封面，后面再换尺度或补场景。竖向素材一帧一图，优先满版且保住主体。横向素材必须两帧一组上下拼接，等比保留全画面，中间留素色分隔。
4. 文案分两遍。先从素材挑能帮读者选餐的一点，写清服务和订餐入口。成稿后再删重复、理句序，逐项核对新增的业务说法。广州业务默认在标题和话题标明「广州」。正文通常 80–150 字，写到信息说完为止。标题和话题另计。具体做法见文案指南。
5. 导出或交付前复核。成品按翻图次序命名，首张即封面。用手机阅读尺度看首图和连续两张，核对文案点到的菜、空间和图序。每次交付图集都给标题、短正文、适量话题和对应图片。用图库 CLI 生成 3:4 JPEG，单张尽量控制在 300,000 字节内。研究证据和内部素材编号留在发布文案之外。

去字使用 Video Frame Studio，图集保留真实菜品、份量、设备和工作状态。价格、覆盖区域、资质、客户、餐量和操作承诺以用户提供的事实为准。公开输出前处理用户未授权公开的身份信息。原始素材、待发文案和渲染产物留在任务输出目录，例如 `runs/xhs-<job>/`。

## 什么时候查资料

- 云环境直接使用仓库内这套技能及其参考文件。个人口吻用用户确认的真稿校准，样本及衍生口吻档案保存在本地忽略目录或文件中。
- 写稿、改稿或审稿时读 [餐饮配送文案指南](references/delivery-copy.md)。选图或改图集时读 [图序](references/editorial-patterns.md) 中对应主题。
- 用户要求做小红书研究，或需要新的案例验证选择时，读 [原帖证据](references/observed-notes.md)。云端有可用的 Agent Reach 或登录浏览器时可做只读站内检索。用户要求实时原帖时应区分搜索摘要、实际正文、看过的轮播页和已加载评论。没有站内访问时直接使用提供的素材和已记录样本，并说明本次证据来源。
